API інформаційної системи ветеринарної клініки (1.0.0)

Download OpenAPI specification:

REST API для обліку власників і пацієнтів, ведення медичних карток, керування розкладом прийомів та обліку медикаментів ветеринарної клініки. Джерело вимог: spec/srs.md v1.0, spec/addendum-001-api-decisions.md, spec/addendum-002-api-contract-decisions.md.

Загальні правила

  • Формат. JSON (application/json), поля в camelCase, ідентифікатори UUID, час за ISO 8601 із зсувом (відповіді повертаються в часовому поясі клініки Europe/Kyiv), дати без часу у форматі YYYY-MM-DD (трактуються в часовому поясі клініки, межі діапазонів from і to включно).
  • Автентифікація. Заголовок Authorization: Bearer <token>. Токен видається POST /auth/login (дійсний 8 годин). Активність облікового запису перевіряється на кожному запиті.
  • Ролі. ADMIN (адміністратор) і VETERINARIAN (лікар). Кожна операція вказує дозволені ролі в розширенні x-roles. Роль перевіряється на кожному ендпоінті (REQ-F-004, REQ-NF-002).
  • Порядок перевірок. 401, потім 403 (роль), потім 400/422, потім 404, потім 409. Винятки: 403 NOT_ASSIGNED_DOCTOR і NOT_VISIT_AUTHOR визначаються після завантаження об'єкта.
  • Пагінація колекцій. Параметри page (≥ 1, за замовчуванням 1) і pageSize (1–100, за замовчуванням 20); відповідь має вигляд {items, page, pageSize, total}. Сортування фіксоване для кожної колекції.
  • PATCH. Передані поля змінюються, відсутні лишаються. Невідоме або незмінюване поле і порожнє тіло дають 422. Значення null очищає необов'язкове поле.
  • Видалення. Фізичного видалення сутностей предметної області немає: DELETE на будь-який ресурс повертає 405 із заголовком Allow (REQ-F-016). Деактивація, архівація та скасування виконуються зміною статусу.
  • Помилки. Єдина модель Error (див. компоненти) для всіх відповідей 4xx і 5xx. Кожна відповідь містить заголовок X-Request-Id, що збігається з traceId у тілі помилки; відповідь 405 містить заголовок Allow зі списком дозволених методів; відповідь 401 містить WWW-Authenticate: Bearer.
  • Простежуваність. Розширення x-requirements у кожній операції містить REQ-ID вимог SRS, які вона реалізує. Наскрізні вимоги REQ-F-004 і REQ-NF-002 (перевірка ролі на кожному ендпоінті, 401/403) діють для всіх операцій і наведені в x-cross-cutting-requirements.

Відповідність термінам предметної області

Термін глосарію SRS §3 У API
Власник (Owner) ресурс owners, схема Owner
Пацієнт (Patient) ресурс patients, схема Patient
Запис на прийом (Appointment) ресурс appointments; статуси «Заплановано», «Завершено», «Скасовано» мають значення SCHEDULED, COMPLETED, CANCELLED
Прийом (Visit) схема Visit, підресурс запису appointments/{appointmentId}/visit
Медична картка (Medical Record) не окремий ресурс: хронологія прийомів patients/{patientId}/visits і статус пацієнта (ACTIVE, ARCHIVED, «Архівна картка»)
Слот розкладу (Schedule Slot) схема Slot у відповіді doctors/{doctorId}/schedule (FREE, BOOKED)
Конфлікт розкладу (Schedule Conflict) відповідь 409 з кодом SLOT_TAKEN
Медикамент (Medication), Каталог медикаментів ресурс medications, схема Medication
Залишок препарату (Medication Stock) поле quantity медикамента, операція adjust-stock
Адміністратор (Administrator) роль ADMIN
Лікар (Veterinarian) роль VETERINARIAN; у шляхах і полях використано скорочення doctor (/doctors, doctorId)
Сповіщення про низький залишок (REQ-F-047, поза глосарієм) ресурс notifications, тип LOW_STOCK

Основні позитивні сценарії

Приклади запитів і відповідей для основних операцій наведено в полях examples (запити: valid, відповіді: success) і пов'язані спільними даними: лікар Іваненко О.П., власниця Коваленко М.І., пацієнт Барсик, препарати Амоксицилін і Новокаїн. Наскрізний сценарій: login, createUser (лікар), createOwner, createPatient, getDoctorSchedule, createAppointment, rescheduleAppointment або cancelAppointment, createVisit (списання медикаментів, BDD §9.2), listPatientVisits, adjustMedicationStock, listNotifications. Негативні сценарії описано відповідями 4xx кожної операції (код і приклад на кожну помилку).

Auth

Автентифікація

Вхід у систему

Повертає bearer-токен. Невірні email або пароль дають 401 INVALID_CREDENTIALS (однаково для невідомого email). Якщо пароль вірний, а обліковий запис деактивовано, повертається 403 ACCOUNT_DEACTIVATED. Вимоги: REQ-F-003, REQ-NF-001.

Повертає всі слоти по 30 хвилин у межах робочих годин (09:00–18:00) робочих днів (понеділок–п'ятниця) за діапазон дат from…to включно (не більше 7 днів), вільні й зайняті.
