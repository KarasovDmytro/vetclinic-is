# Addendum 001 до SRS v1.0: рішення, потрібні для проєктування API

| Дата | 2026-10-28 |
| Статус | **Approved** (затверджено людиною KarasovDmytro, 2026-10-28; усі пункти AD-01…AD-09 без змін) |
| Підстава | Проєктування REST API за SRS v1.0. SRS §6.4: суттєві рішення фіксуються письмово |

Пункти AD-01…AD-04 закривають чотири діри з TSK-002. Пункти AD-05…AD-09 виявлено під час визначення ресурсів API, тому обсяг TSK-002 розширюється. Жодне рішення не додає функціональності поза SRS §2.1: вони лише уточнюють поведінку там, де SRS мовчить або суперечить сам собі.

---

## AD-01. Автентифікація (REQ-F-001, F-003, F-004, NF-001)

**Діра:** SRS припускає вхід і 401, але не описує вхід, токен і створення першого адміністратора.

**Рішення:**
1. Вхід за `email` і `password`. Успішна відповідь містить bearer-токен (JWT) із терміном дії 8 годин. Refresh-токенів і ендпоінта виходу немає: вихід означає, що клієнт відкидає токен.
2. Невірний email або пароль дають 401 з однаковим повідомленням (без розкриття, чи існує email).
3. Якщо пароль вірний, а обліковий запис деактивовано, відповідь 403 з кодом `ACCOUNT_DEACTIVATED` (REQ-F-003).
4. Активність облікового запису перевіряється на кожному запиті: токен деактивованого користувача перестає діяти одразу.
5. Перший адміністратор створюється при розгортанні (seed або міграція), а не через API, бо `POST /users` доступний лише адміністратору.
6. Пароль задає адміністратор при створенні облікового запису. Зміна пароля та відновлення доступу в SRS немає, у API не вводяться.
7. Деактивація останнього активного адміністратора заборонена (409), щоб система не втратила керування. Це обмежувальне уточнення REQ-F-002 («будь-який обліковий запис»).

## AD-02. Сповіщення про низький залишок (REQ-F-047)

**Діра:** канал сповіщення не визначено.

**Рішення:**
1. Канал внутрішній: ресурс `Notification` типу `LOW_STOCK`, доступний лише адміністратору. Email, push і зовнішні канали недопустимі (поза межами SRS §2.2).
2. Сповіщення створюється в тій самій транзакції, що й збереження прийому, коли залишок після списання **строго нижчий** за мінімальний поріг.
3. Якщо для цього препарату вже є непрочитане сповіщення, нове не створюється.
4. Якщо поріг не заданий, сповіщення не створюються.
5. Ручне коригування залишку (AD-08) сповіщень не створює. Стан «залишок нижчий за поріг» видно з поля `lowStock` у препарату.
6. Адміністратор позначає сповіщення прочитаним.

## AD-03. Скасований запис і слот (REQ-F-021, F-023, F-024, F-025)

**Діра:** не визначено, чи звільняє слот скасований запис і які переходи статусів допустимі.

**Рішення:**
1. Слот зайнятий лише записами у статусах *Заплановано* і *Завершено*. Скасований запис слот звільняє. Конфлікт за REQ-F-023 визначається тільки серед зайнятих слотів.
2. Допустимі переходи статусів:

| З | У | Як |
|---|---|---|
| *Заплановано* | *Заплановано* (інший слот) | перенесення адміністратором (REQ-F-024) |
| *Заплановано* | *Скасовано* | скасування адміністратором (REQ-F-025) |
| *Заплановано* | *Завершено* | лише збереженням прийому лікарем (REQ-F-027) |
| *Завершено*, *Скасовано* | будь-який | заборонено (409) |

3. Перенесення можливе лише на інший вільний слот **того самого лікаря**. Зміна лікаря виконується скасуванням і створенням нового запису.
4. Початок слота має бути на :00 або :30 (REQ-F-020), інакше 422.

## AD-04. Архівна картка та записи на прийом (REQ-F-015, F-021, F-035)

**Діра:** не визначено, чи можна записати архівного пацієнта і що з його існуючими записами.

**Рішення:**
1. Створити або перенести запис для архівного пацієнта заборонено (409).
2. Архівування пацієнта з записами у статусі *Заплановано* відхиляється (409): адміністратор спочатку скасовує їх явно. Прихованих побічних ефектів немає.
3. Зворотної операції (розархівування) немає: SRS її не описує (R-14). Архівування необоротне через API.

## AD-05. Межі сітки розкладу (REQ-F-020)

**Діра:** SRS не визначає робочі години, тож не можна побудувати сітку.

**Рішення:**
1. Робочі години клініки є конфігурацією системи: за замовчуванням 09:00–18:00 (18 слотів на добу), усі дні тижня. Індивідуальні графіки лікарів не вводяться.
2. Часовий пояс клініки є конфігурацією, за замовчуванням `Europe/Kyiv`. API приймає й повертає час у ISO 8601 з зсувом.
3. Запис дозволено лише в слот, що лежить у межах робочих годин (інакше 422).

## AD-06. Читання довідкових даних лікарем (SRS §4.1, REQ-F-030, F-034, F-044)

**Діра:** §4.1 вказує «Немає доступу» до власників і пацієнтів для лікаря, але F-030 дає йому доступ до картки будь-якого пацієнта, а F-044 дає вибір препарату зі списку.

**Рішення:**
1. Лікар має **лише читання** власників і пацієнтів, включно з пошуком (REQ-F-017). Створення та зміна лишаються за адміністратором. Дані пацієнта та власника не містять діагнозів чи призначень.
2. Лікар має **лише читання** каталогу медикаментів.
3. Для вибору лікаря в розкладі обидві ролі мають довідник лікарів (id, ПІБ, активний), окремий від адміністративного списку користувачів (REQ-F-005 лишається в силі).
4. Лікар бачить розклад усіх лікарів (REQ-F-026).

## AD-07. Життєвий цикл прийому (REQ-F-027, F-032, F-033, F-035, F-045)

**Діра:** не визначено, хто може зберегти прийом, чи можна його редагувати і що тоді з залишками.

**Рішення:**
1. Прийом створюється лише для запису у статусі *Заплановано*, і лише лікарем, якому цей запис призначено. Інший лікар отримує 403. Один запис має не більше одного прийому.
2. Збереження прийому атомарно (REQ-NF-005): створює прийом, ставить запису *Завершено*, списує препарати, створює сповіщення (AD-02). Збій у будь-якому кроці скасовує все.
3. Прийом без витрачених медикаментів допускається.
4. Один препарат не може повторюватися в одному прийомі (422).
5. Збережений прийом можна редагувати лише його автору і лише поки картка не архівна: діагноз, призначення, нотатки. **Перелік медикаментів після збереження незмінний**, повторного списання немає (R-09). Помилки корегує адміністратор через AD-08.

## AD-08. Одиниці та коригування залишку (REQ-F-042, F-044, F-046, F-048)

**Діра:** тип кількості та форма коригування не визначені.

**Рішення:**
1. Кількість і залишок є цілими невід'ємними числами, одиниця виміру не моделюється. Витрачена кількість у прийомі ≥ 1.
2. Ручне коригування задається **зміною** (додатна або від'ємна, ненульова), а не новим абсолютним значенням: це безпечно при паралельному списанні. Результат менший за 0 відхиляється (REQ-F-048).
3. Залишок змінюється тільки через коригування та через збереження прийому. Звичайне редагування препарату (назва, поріг) залишок не змінює.

## AD-09. Відсутність фізичного видалення в API (SRS §4.1 «Повний CRUD»)

**Діра:** §4.1 називає права «повний CRUD», хоча REQ-F-002, F-015, F-016, F-025 вимагають деактивації, архівації та скасування замість видалення.

**Рішення:** у API немає жодної операції `DELETE` для сутностей предметної області. Деактивація, архівація і скасування виконуються як зміна статусу. Виклик `DELETE` на ресурс повертає 405.
